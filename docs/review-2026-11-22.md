## 1. Fixed in v1.0.2

### 1.1 Exact mode refused every large real product or quotient (release blocker)
- Symptom: CI `FAIL fresh huge (10^400+1)/7 unverified`. It failed the v1.0.1 PR head run and the v1.0.1 Pages deploy, so **the live site was still 1.0.0**. It is broader than that row: `10^400/7`, `10^400*2` and `10^400*i` were all "couldn't verify". Any real or imaginary product or quotient past about 10^226 was refused.
- Cause: `refusedResult()` in `lib/eml/exact.ts`, the rule "a part cancelled to 0 beside a nonzero part". A real result has im = 0, and multiplying by a huge X passes through 1/X, so `firstTiny ≈ −X.e`, `need ≈ 2·X.e + 30` was past the cap, and the code refused.
- Fix: per-component small-value channels (`tinyRe`, `tinyIm`, `partsFloor`, `minParts`, also in the pure cache). A value with both parts nonzero records into both channels (exp and ln mix them). The rule reads the channel of the component that came out 0.
- A first attempt (retry at the cap instead of refusing) was wrong: it certified `((1+10^-500)-1)+i/2` as `0.5i`. It was dropped.
- Rows: `10^400/7`, `10^400*2`, `10^400*i`, `-(10^400)/3`, `10^300*10^100` kept. `i*((1+10^-500)-1)+1/2` refused.

### 1.2 artanh and arctan branch depended on how the argument was built (certified wrong values)
- Found by differential fuzzing against mpmath (§4). `atanh(4.861)` gave −iπ/2 (documented), but `atanh(1.694^3)`, `atanh(1.5^3)` and `atanh(1.694^2)` gave +iπ/2. `atan(-2i·asinh 9)` gave +π/2 − 0.1746i (mpmath: −π/2 − …).
- Cause: the special case for reals above 1 runs only when the range table has a point. Otherwise ½·Log((1+z)/(1−z)) lands on the other bank. Off the axis that formula is fine; it fails only on the cuts.
- Fix (`lib/eml/library.ts`): `tArtanh` generic = `Log(√(1+z)/√(1−z))`, an exact identity for the DLMF 4.37.24 atanh. No 2πi is lost, because half a difference of two principal Args stays in (−π, π). `tArctan` generic = `−i·artanh(iz)`. Both identities were checked against mpmath at 6000 random points with 0 mismatches. Cost: K +5 to 9% (`atanh(0.5)` 507 → 547, `atan(0.5)` 713 → 777).
- The rejected alternative ½(ln(1+z) − ln(1−z)) is correct but makes atanh about 7× longer (two complex logs need rotSub).

### 1.3 The record certifier accepted a 10^(−307) impostor as −iπ
- `acceptsConstantProgram` (`lib/eml/golf.ts`) accepted `11111111E11E1EE1EEEEEE1E1E11E1E1EEE` (K 35) as −iπ. Its value is −9.0×10^(−307) − i(π − 4×10^(−307)). The trace shows a genuine 6.3×10^(−306) i from exp(−701.88 − 481.10i). A ball and a 280-digit compare both stop at about 10^(−240).
- Fix: the certifier also requires `exactReport(node).unverified !== true`. Every word in `best-known.json` is still certified (checked).
- Impact: the repo's K 35 golf search would have published a false −iπ record at K 35. The known −iπ is K 45.

### 1.4 Presses before hydration were dropped (the flaky "1, 1, EML showed 0")
- The static HTML contains working-looking keys before React hydrates. The CI boot loop waited only for the elements, so clicks were lost and the screen stayed "0".
- Fix: `<main data-ready="1">` once hydrated (via `useSyncExternalStore`). CI waits for it, and smoke asserts it is absent from the static HTML and present after mount.
- A related defect is also fixed: an effect wrote `modelRef.current = model` after each render, which could roll the ref back past newer handler writes. The handlers are now the only writers of `modelRef`/`modeRef`, and `textRef` is assigned during render.

### 1.5 Aesthetics and consistency
- All text was Times New Roman: `--font-sans` was used everywhere and defined nowhere, and an undefined `var()` invalidates the whole `font-family`. It is now defined in `app/globals.css` as a system stack.
- The evaluation radio (hardware/exact) showed the selected option only by a 3 px press with the same green, so the raised, unselected key looked active. The unselected key is now dimmed.
- `formatDec`'s hidden-tail reveal fired whenever places 13–14 were 0 (about 1% of values): `0.0199308684580096i` became `0.019930868458i`. It still reveals 0.5 − 10^(−72) and 1 − 10^(−72).

### 1.6 CI speed (it took about 20 min, and `main` re-ran it all)
- Before: one job. `eml:check` alone took 1156 s, followed by both golden modes, build and Chrome in sequence.
- After: parallel jobs `static`, `check` (6-way matrix, `EML_SHARD=i/6`), `golden` (2-way matrix) and `site` (build, Chrome, upload). Every top-level block of `check.ts` is gated by `shardTurn(id)`. Weights in `lib/eml/check-shards.json` are assigned greedily, heaviest first. The union of shard outputs equals the unsharded output line for line. Locally, 830 s becomes 167 s wall.
- Still open: `pages.yml` re-runs all of CI on every push to `main` after the PR already passed. Options: skip when the same tree passed, or use a merge queue. The golden in-process run (about 5 min) is now the critical path, and its rows could be sharded the same way.

### 1.7 Windows portability
- `check.ts` (isolate rebuild) and `check-properties.ts` (cold arcsin) spawned `node_modules/.bin/tsx`, which fails on Windows (status null). They now use `process.execPath` with `tsx/dist/cli.mjs`. The golden harness spawned `node_modules/esbuild/bin/esbuild` (a native binary on Linux, a JS file on Windows) and now uses `buildSync` from esbuild's API. `esbuild` is a pinned devDependency (0.28.2, the version already in the lockfile).

- Lessons learned, which also apply to `golf.ts`:
  - One representative per float key loses true words. `1111EE1E1E1EE11EE` is −1 + 4.4×10^(−114), float-identical to −1. Use at least 2 slots (`golf.ts` uses 4, correctly).
  - A 250-digit check is not enough. 322 hits that passed at 250 digits fail at 700, with residues between 10^(−250) and 10^(−690).
- `acceptsConstantProgram` can only certify **dyadic** targets, because it compares against a float. 1/3, ln 2 and e±1 are always rejected. The 1/3 records go through a separate path in `check.ts`. A target-as-exact-expression API would fix that.

## 3. The binary representation — what it is good for

- A press word is a Łukasiewicz (Polish) code: 1 → bit 1, EML → bit 0, K = 2n − 1 bits. Every program starts `11`, ends `0`, and keeps a positive stack. So the binary value is always even, and valid words are a small fraction of K-bit strings: there are Catalan(n−1) ≈ 2^(K − 1.5·log2 n − O(1)) programs. At K 39 that is 2^30.7 programs for 39 bits.
- The program number (`#N`, `programIndex.ts`) is the optimal dense code for programs, ordered by length. At K 39 it saves about 8 bits over the press string.
- Values are far fewer than programs. Only 16% of K 39 programs give a value not seen at a shorter length (§2 table), and distinct values grow about 3.25× per extra 1 against 3.7× for programs. An index into distinct values would save another 3 bits at K 39. This is the right object for a "value catalogue".
- Practical uses:
  1. Shareable IDs (`?p=#N`). A URL parameter is not implemented yet.
  2. Deterministic sharding and resumable searches: rank ranges map to workers.
  3. Uniform random programs of a given length (`unrank(random < Catalan)`). A "random program" key would be cheap.
  4. Prev/Next browsing. Its value is low, because neighbouring numbers are not similar values.
- Consistency issue (OPEN): the UI uses three notations for the same word. The note says `1 1 E`, the legend says `110`, and the program field says `#1`. The program field also accepts both `#110` and `110`, which mean different programs. Pick one display form (suggestion: `11E` everywhere, with `#N` only as the ID) and make the parser's ambiguity explicit in the placeholder.

## 4. Differential fuzzing (how 1.2 was found)

800 random expressions (depth ≤ 3, every unary function, + − × ÷ ^, complex leaves) went through exact mode and were compared with mpmath at 60 digits, principal branches. Exact mode honestly refused 7. Certified mismatches: atanh on the cut (1.2), atan on the cut (1.2), and `asin(atan(-i))`, which is a pole and reported "indeterminate" (fine). After the fixes, the atanh rows match. Scripts were scratch only; recreating them takes about 60 lines (Python generator, TS runner calling `compileExpression` + `exactReport`, mpmath comparer). Turning this into `scripts/fuzz-mpmath.*` with a fixed seed would make a good nightly job.

## 9. Second round (same day): more fixes, a new record, and proofs

Fixed (all in PR #46):
- **Huge-sum products certified wrongly.** `(10^400+i)*2` was certified as `2×10^400`, dropping 2i, and `2*(10^400+π)` likewise. `hidesBeside` in `exact.ts` looked for the remembered-huge-sum marker only 8 gates deep and 64 steps, and the product word hid it. The walk now covers the whole DAG (memoized). This surfaced because 1.0.2's channel fix stopped refusing these by accident.
- **CI golden sharding.** `GOLDEN_SHARD=i/N` evaluates every Nth sorted corpus row. Shard 0 also checks REMOVED rows and the row count. CI runs 2 modes × 4 shards. A tampered row is caught by its shard. The whole CI now takes about 5½ min (it took 20+).

Verification sweeps, with nothing wrong found:
- A branch-cut sweep: ln, sqrt, cube roots, powers of negatives, asin, acos, acosh, asinh, atanh and atan at cut points, each built several ways (83 probes). All match mpmath.
- A variable fuzz: 300 expressions in x and y at random points, cut points included. 0 certified wrong values.
- A deep fuzz: 1500 constant expressions of depth up to 4. 0 certified wrong values. The 4 flagged rows go through poles or ln 0, where the app says "indeterminate".
- The float flag (`beyondFloatBound`), checked against mpmath over 1088 certified rows: 0 silent-wrong floats and 0 false alarms. The underflow path is separate.
- Program ranking: rank and unrank round-trip and are ordered across all 6918 programs with K ≤ 19 and 2000 random words up to K 601.

New record:
- **−iπ (lower cut) without ln 0 at K 47** (was K 55): `11111E1E1EEEE11111111E1E1EEEE1E1E1EEE1EE11E1EEE`. Found by `tools/emlsearch` `MITM=1`, which inverts the last gate. For every value `a` with K ≤ 35 and target `t`, the needed `b = exp(exp(a) − t)` is looked up among 37 M stored values, so it reaches words up to K 71 whose two halves are each at most K 35. The word passes 100 and 700 digits, exact mode certifies it, `acceptsConstantProgram` accepts it, and the imaginary part is −π at 30–480 digits. It also found −4 (K 53) and ±5 (K 63). For π, i, √2 it found nothing within that reach, so the constructions stand.

Proofs (`tools/minimality/decide.py`, reproducible):
- It re-derives every claim in docs/minimality.md, PROVED with nothing undecided, including the four K 17 programs the original certificate did by hand.
- **New: +iπ (lower cut, ln 0 allowed) is minimal at K 21.** All 6918 programs with K ≤ 19 are excluded.
- Method: interval arithmetic (mpmath.iv) plus exact k·π tags; symbolic forms as integer combinations of `exp(..)`, `ln(..)`, `1` and `iπ` atoms, with sound rewrites; towers as ±exp(L) and tiny values as exp(−L); and signed infinitesimal offsets. Offsets are what separate impostors such as `11E1E111E1E1E1E1EEE` = iπ + 10^(−1656519), which mpmath at 2000 digits cannot tell from iπ.
- A built-in self-test checks that 18 known genuine words are never excluded for their own value. It runs before every claim. If it fails, the tool exits 2.
- Still open: +iπ without ln 0 at K 23 (16 K 21 programs undecided) and −2 at K 25 (188 undecided). No counterexamples. Extending the tower rules (log of a "huge" complex value, towers minus towers) is the next step.

Lessons for the next agent:
- Float-keyed dedup needs at least 2 representatives per key.
- A 250-digit check misses 10^(−307) residues, and even 2000 digits miss tower-absorbed terms near 10^(−1656519). Only symbolic sign tracking or exact mode's refusal rules see those. The app's exact mode correctly refused both tower impostors of +iπ at K 21.
- A "best so far" filter lets an impostor hide genuine longer words. Don't filter on it.
